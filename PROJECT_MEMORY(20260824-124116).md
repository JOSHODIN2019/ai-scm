# 1. PROJECT VISION

We are building an **AI-Driven Software Configuration Management System** for academic research and practical demonstration.

The system helps developers understand software changes by analyzing information such as:

- commit messages
- changed files
- code differences (diffs)
- author and commit date

A pre-trained Large Language Model (LLM), or a clearly separated local/mock AI service during development, analyzes a software change and returns:

1. **Change Type**
   - Bug Fix
   - New Feature
   - Refactoring
   - Configuration Change

2. **AI-Assessed Risk Level**
   - Low
   - Medium
   - High

3. **Short Explanation**

The system also stores previous analyses and provides an evaluation area where AI predictions can be compared with expected labels using:

- Accuracy
- Precision
- Recall
- F1-score
- Confusion matrix

The system is an **AI-assisted decision-support tool**. It does not automatically modify source code and does not replace the developer's final decision.

# 6. AI PROVIDER POLICY

The project will use an **OpenAI LLM through the OpenAI API**.

OpenAI API usage is not assumed to be free. API billing is separate from a ChatGPT subscription. Before making real API calls, clearly inform the user if an API key, billing setup, or paid usage is required.

The architecture must isolate OpenAI integration behind an AI service so the rest of the application does not depend directly on OpenAI-specific implementation details.

Preferred structure:

```text
Frontend
   ↓
Backend API
   ↓
AI Service
   ↓
OpenAI API / LLM
```

The OpenAI API key must:
- exist only on the backend
- be stored in `.env`
- never be placed in frontend JavaScript
- never be committed to GitHub

If OpenAI API access is unavailable during development, create a clearly separated Mock AI Service only as a temporary fallback. The mock must never be presented as the actual OpenAI model.

Do not secretly introduce another LLM provider.

Do not replace OpenAI with a local model unless the user explicitly approves the change.

# 7. AI RESPONSE CONTRACT

The AI service must return a predictable structure:

```json
{
  "change_type": "Bug Fix",
  "risk_level": "Medium",
  "explanation": "The change modifies authentication logic and may affect existing login behaviour."
}
```

Only valid change types:

```text
Bug Fix
New Feature
Refactoring
Configuration Change
```

Only valid risk levels:

```text
Low
Medium
High
```

If an LLM returns invalid output, the backend must validate and handle it safely.

# 8. AI ANALYSIS PROMPT

Use a structured prompt similar to:

```text
You are a software configuration management assistant.

Analyze the following software change.

Commit message:
{commit_message}

Changed files:
{changed_files}

Code difference:
{code_diff}

Classify the change into exactly one of:

Bug Fix
New Feature
Refactoring
Configuration Change

Then assign exactly one AI-assessed risk level:

Low
Medium
High

Return:

Change Type:
Risk Level:
Explanation:

Keep the explanation short and base it only on the information provided.
Do not claim certainty about future software failures.
```

The wording can improve as testing progresses, but the output contract must remain stable unless an approved architectural change is made.

# 9. RISK ASSESSMENT PRINCIPLES

The system must not claim that it can perfectly predict real-world software failure.

Use the wording:

**AI-assessed risk level**

rather than:

**Guaranteed risk**

The AI may consider:

- number of files changed
- size of code differences
- type of change
- authentication/security-related areas
- database-related changes
- configuration changes
- dependency changes
- potentially sensitive modules

The result is advisory.

The developer remains responsible for the final decision.
